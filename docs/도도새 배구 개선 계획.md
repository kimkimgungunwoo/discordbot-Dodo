# 도도새 배구 개선 계획

작성일: 2026-09-25  
상태: 사용자 승인 후 구현 완료. 아래 계획과 마지막 절의 구현·검증 결과를 함께 참고한다.

## 1. 목표와 제안값

| 요청 | 구현 방향 | 최초 적용 후보 |
| --- | --- | --- |
| 공을 조금 느리게 | 공에만 비행 시간 배율 적용 | 기존 대비 90% 속도 |
| 일반 리시브 강화 | 위쪽 힘과 타점에 따른 가로 반발력 증가 | 위쪽 힘 12~14 → 16~18, 가로 계수 offset/4 → offset/3, 상한 12 → 16 |
| 멀티 상대 움직임 개선 | 상대 입력의 조기 활용, 예측 보정 완화, 렌더링 보간 | 화면 보정 약 50~100ms, 상황별 초기화 |

수치는 시작점이다. 아래 검증 기준을 만족하도록 구현 중 조정하고 최종값과 검증 결과를 보고한다. 90% 속도는 같은 비행 구간에 약 11% 더 긴 시간이 걸리는 수준이다.

## 2. 공 속도: 기존 물리의 성격 유지

현재 `physics.ts`는 매 tick 중력을 속도에 더한 뒤 위치를 갱신한다. 속도 값만 줄이면 비행 높이와 도달 거리가 함께 줄어드는 문제가 있다.

공의 비행 시간 배율을 별도 상수로 두고, 위치 이동과 중력 적분에 일관되게 반영한다. 목표는 기존 공 궤적을 더 천천히 따라가게 하는 것이다. 기존 이산 적분과의 차이를 확인하며 부분 시간 적분을 설계한다. 중력 계수, 벽·네트 반사 규칙, 천장 충돌 규칙, 스파이크 방향 및 상대적인 강도는 유지한다.

캐릭터 이동·점프, 게임 tick 60Hz, 준비·득점 대기시간은 유지한다. 공만 느려지므로 움직이는 캐릭터와 만나는 시점은 바뀐다. 충돌이 포함된 경기 전체의 궤적까지 기존과 완전히 같다는 의미는 아니다.

AI도 동일한 비행 계산을 사용하도록 맞춘다. 현재 일부 AI는 중력과 위치를 직접 계산하므로 공만 수정하면 착지 예측이 어긋날 수 있다. 난이도별 예측과 시뮬레이션을 함께 확인한다.

## 3. 일반 리시브: 타점을 잡으면 네트를 넘길 수 있게

현재 일반 리시브는 위쪽 힘이 12~14이며, 가로 속도는 공과 캐릭터 중심의 차이를 4로 나눈 값이다. 중심에서 받으면 거의 수직으로 뜨고, 가로 힘이 작은 타점에서는 네트까지 도달하기 어렵다.

위쪽 힘을 우선 16~18로 높이고, 가로 반발력을 `offset/3`, 상한 16으로 강화한다. 스파이크의 위쪽 속도도 현재 리시브용 `lift`를 공유하므로 계산을 분리해 일반 리시브 강화가 스파이크까지 의도치 않게 강화하지 않도록 한다.

타점으로 방향을 정하는 기존 조작감을 유지한다. 왼쪽 선수는 몸 오른쪽, 오른쪽 선수는 몸 왼쪽으로 받아 상대 코트에 보낼 수 있게 한다. **정중앙 리시브는 수직에 가깝게 뜨며, 모든 리시브를 자동으로 상대 코트로 보내지는 않는다.**

성공 기준은 양쪽 코트 중앙 부근에서 지상 일반 리시브를 했을 때, 상대 코트 방향으로 적절히 치우친 타점이면 공격 버튼 없이 네트를 넘어가는 것이다. 공 반지름까지 포함해 네트 통과 여부를 확인한다. 천장 충돌이 지나치게 자주 발생하면 위쪽 힘과 가로 힘의 비율을 조정한다. 반복 접촉 방지와 다이빙 접촉 규칙도 확인한다.

## 4. 멀티: 입력 예측과 화면 표시 개선

### 코드에서 확인한 원인 후보

- 서버는 `INPUT`을 즉시 중계하지만 클라이언트는 이를 사용하지 않는다. 양쪽 입력이 모인 `FRAME`을 받아야 상대 입력을 갱신한다.
- 클라이언트는 확정 상태보다 6tick 앞을 예측하고, 마지막 상대 입력을 계속 적용한다. 상대가 방향을 바꾸거나 점프하면 오차가 커질 수 있다.
- 재계산한 예측 상태를 화면에 즉시 적용하므로 위치 보정이 순간이동처럼 보일 수 있다.
- 확정 프레임이 쌓이면 한 번에 여러 tick을 처리하며, 렌더링은 tick 사이의 위치를 보간하지 않는다.

이는 코드상 후보이며 실제 지연 환경에서 원인별 영향을 재현해 확인한다.

### 변경안

1. 서버가 중계한 상대 `INPUT`을 tick별로 보관한다. 해당 tick 입력이 있으면 예측에 우선 사용하고, 없을 때만 가장 최근의 유효한 상대 입력을 사용한다. 확정된 tick, 이전 경기 메시지, 비정상 미래 tick은 제외하고 버퍼를 정리한다.
2. 확정 상태와 예측 상태에 더해 화면 표시용 상태를 분리한다. 상대 위치의 작은 보정 오차는 약 50~100ms 동안 줄인다. 표시용 좌표는 충돌 계산, AI, 점수 및 결과 전송에 사용하지 않는다.
3. 렌더링 프레임 사이 위치를 보간한다. 내 캐릭터의 즉시 입력 반응을 우선하며, 상대 보정 때문에 내 입력에 같은 지연을 추가하지 않는다. 공에도 보간을 적용하되 충돌 전후를 가로질러 네트를 통과하는 것처럼 보이지 않게 처리한다.
4. 득점·서브·재접속·재경기·이력 복구·경기 종료 및 큰 위치 오차에서는 보정 이력을 초기화한다. 관전에는 내 입력 예측을 적용하지 않고 확정 프레임 표시를 부드럽게 한다.
5. 현재 6tick 입력 선행량과 프레임 소비 방식을 지연 실험으로 확인한다. 초기 변경에서는 유지하고, 병목으로 확인될 때만 서버의 최대 12tick 허용 범위 안에서 조정한다. 확정 진행이 멈추었을 때 입력을 무제한 보내거나 상대를 계속 이동시키지 않는다.

결과 판정은 계속 확정 프레임을 기준으로 한다. 통신이 실제로 장시간 멈추는 경우까지 화면 보정으로 없앨 수는 없으며 기존 연결 대기·복구 흐름을 유지한다.

## 5. 수정 예상 범위

- `games/client/src/volleyball/constants.ts`: 공 시간 배율, 리시브 관련 상수.
- `games/client/src/volleyball/physics.ts`: 비행 적분, 일반 리시브와 스파이크 계산 분리.
- `games/client/src/volleyball/ai.ts`: 공 비행 예측 일치.
- `games/client/src/volleyball/online-session.ts`: tick별 상대 입력 활용, 예측·확정 상태 관리.
- `games/client/src/volleyball/main.ts`, `session.ts`, 필요 시 표시 전용 모듈 및 `render.ts`: 렌더링 보간과 보정 초기화.
- 클라이언트 테스트 및 필요 시 서버 중계 테스트: 물리와 동기화 회귀 검증.

서버는 이미 상대 입력을 중계하므로 현재 계획에는 통신 프로토콜 변경이 필요하지 않다.

## 6. 검증과 완료 기준

### 물리·리시브

- 자유 비행의 궤적과 도달 시간을 비교해 속도 감소와 궤적 유지 정도를 확인한다.
- 양쪽 코트에서 일반 리시브만으로 네트 통과가 가능한 타점·위치 조합을 테스트한다.
- 중앙·역방향 타점, 점프·다이빙 리시브, 스파이크 방향, 네트·벽·천장 충돌, 득점 판정을 확인한다.
- 동일 seed와 입력에서 동일 결과가 나오는지, 입력 상태를 변형하지 않는지 검증한다.
- 모든 CPU 난이도에서 비정상 수치나 예측 불일치 없이 경기가 진행되는지 확인한다.

### 멀티

- 동일 입력 시나리오로 변경 전후를 비교한다. 정상 통신 외에 RTT 50/100/200ms와 지연 변동·프레임 묶음 도착을 재현한다.
- 상대의 직선 이동·급정지·방향 전환·점프에서 화면 위치의 급격한 보정 빈도와 크기를 비교한다. 목표는 순간 보정을 줄이면서 표시 위치가 실제 예측 위치에 지속적으로 뒤처지지 않는 것이다.
- 양쪽 플레이어와 관전자의 동일 확정 tick에서 물리 상태·점수·종료 결과가 일치하는지 확인한다.
- 재접속·관전 중도 입장·득점 초기화·재경기·긴 입력 중단에서도 이전 입력이나 표시 보정이 남지 않는지 검증한다.
- 클라이언트와 서버의 기존 테스트 및 빌드를 실행하고, 가능한 로컬 브라우저 환경에서 두 플레이어 화면을 확인한다.

물리 변경은 같은 경기 참가자 모두에게 같은 클라이언트 버전이 적용되어야 한다. 적용 시 진행 중 경기와 섞이지 않게 새 경기에서 확인한다.

## 8. 구현 및 검증 결과

- 공 시간 배율 0.9, 일반 리시브 위쪽 힘 16~18, 가로 반발 `offset/3`·상한 16을 적용했다.
- 공의 자유 비행은 기존 이산 궤적을 부분 시간으로 적분한다. 20tick 비행이 기존 18tick 궤적의 좌표에 도달하는 것을 테스트했다. 움직이는 선수와의 충돌 시점은 달라진다.
- 스파이크의 위쪽 힘은 기존 12~14 기반으로 분리해 유지했다. AI의 별도 비행 예측은 공용 비행 함수로 통일했다.
- 상대 INPUT과 아직 소비하지 않은 FRAME의 입력을 tick별 예측에 활용한다. 미래 tick 입력을 과거 tick에 덮어 적용하지 않으며, 확정 상태 진행 시 버퍼를 정리한다.
- `presentation.ts`에서 공의 프레임 보간과 상대 표시 좌표 보정을 담당한다. 상대 표시는 약 90ms에 보정 오차의 95%가 수렴하며, 지속 이동 중에는 짧은 표시 지연이 따른다. 내 캐릭터 좌표는 이 보정을 거치지 않는다.
- 공은 반사·접촉 때 보간을 생략한다. 경기 교체·득점·이력 복구·큰 위치 오차와 탭 복귀에서는 표시 이력을 초기화한다.
- 기존 6tick 선행량과 서버 프로토콜은 유지했다. 긴 네트워크 중단이나 높은 RTT로 인한 확정 진행 정지 자체를 제거하는 변경은 아니다.

검증 결과:

- 클라이언트 테스트 38개 통과: 양방향 일반 리시브 네트 통과, 공 감속 궤적, 스파이크 힘 유지, AI 난이도, 두 플레이어·관전자 동기화, 재접속·재경기, 표시 보정 포함.
- RTT 50/100/200ms에 해당하는 메시지 지연과 3tick 단위 묶음 도착을 모사한 테스트에서 확정 상태 일치 및 FRAME만 사용하는 비교군 대비 상대 위치 예측 오차 감소를 확인했다. 이 검증은 모의 메시지 스케줄 기반이며 실제 네트워크 처리량·브라우저 체감 측정은 아니다.
- 서버 테스트 41개 통과. 실제 로컬 HTTP/WebSocket 연결·입력 중계·이력·콜백·재경기 회귀 테스트 포함.
- 클라이언트 및 서버 빌드 통과.
- 브라우저 제어 도구가 제공되지 않아 실제 두 브라우저 창의 화면·체감 검증은 수행하지 못했다. 배포는 수행하지 않았다.


## 9. 후속 밸런스 조정: 연결구와 결정구 구분

사용자 승인으로 일반 리시브의 가로 반발력을 `offset/3.5`, 상한 11로 낮췄다. 위쪽 힘 16~18과 공 시간 배율 0.9는 유지했다. 제자리 스파이크 가로 속도는 12에서 18, 이동 스파이크는 22에서 26으로 올렸다.

아래 방향 스파이크의 기존 하강 힘과 충돌 규칙은 유지한다. 높은 타점에서 네트 가까이 내리꽂으면 상대 코트로 넘어가지만, 낮은 타점에서는 네트에 막히는 것을 양쪽 코트 테스트로 확인했다. 별도 자동 조준·타이밍 보너스는 추가하지 않았다.

클라이언트 테스트 40개 통과. 일반 리시브의 중앙 네트 통과, 가장 강한 리시브보다 제자리 스파이크가 1.6배 이상 빠른 가로 속도, 고타점/저타점 하강 스파이크, AI 난이도 및 온라인 동기화 회귀 검증을 포함한다.


## 10. AI 공격·수비 조정

- 보통은 현재 타점·공 속도·네트 거리로 비행을 예측해 하강 → 직선 → 띄우기 순으로 네트를 넘길 수 있는 공격을 선택한다. 쉬움의 공격 금지·반응 공백·위치 오차와 보통의 위치 오차는 유지한다.
- 어려움과 극한은 양쪽 수직 방향 스파이크까지 후보에 포함한다. 공을 건드린 횟수의 보상을 낮추고, 상대의 예상 수비 지점까지 거리와 남은 시간에 비해 이동이 가능한지를 평가한다.
- 극한은 24tick, 어려움은 16tick을 탐색한다. 극한은 탐색 중 상대도 이동·공격·수비하는 상황을 함께 계산한다. 실제 사용자의 미래 입력을 읽는 방식은 아니다.
- 어려움·극한에 공 높이 -65 부근의 저공 수비 예측을 추가했다. 걸어서 닿지 않지만 다이빙으로 닿을 수 있는 범위에서 다이빙 후보를 선택한다.
- 클라이언트 테스트 42개 및 빌드 통과. 양쪽 코트 고타점·저타점 공격 선택, 빠른 공 다이빙과 실제 접촉, 온라인 CPU 재생 일치를 확인했다.
- 4개 seed의 좌우 교대 대전에서 어려움과 극한 모두 보통에 4승·합계 28:0이었다. 기존 난이도 테스트는 어려움이 전 경기 7:0인 포화 상태에 한해 극한의 동점을 허용하도록 조정했다. 이 결과만으로 극한이 어려움보다 강하다는 결론을 내리지는 않는다.
- 보통끼리의 대칭 대전 및 별도 어려움/극한 대전에서는 12,000tick 안에 끝나지 않는 긴 랠리가 관찰됐다. 사람 상대의 체감 난이도와 상위 난이도 간 승률 차이는 실전 확인이 남아 있다. 실제 브라우저에서의 화면 검증은 수행하지 않았다.
