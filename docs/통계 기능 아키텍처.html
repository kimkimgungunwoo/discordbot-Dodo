DynamoDB 멀티 테이블 설계. 대부분의 통계 테이블은 서버 ID를 파티션 키로 사용한다.

서버별 데이터 경계

guild_id로 Query한다. 같은 사용자가 여러 서버에 있어도 활동량은 서버별로 분리된다. 순위는 집계 목록을 읽은 뒤 Python에서 정렬한다.

날짜가 없는 시간대 집계

HH는 KST의 0~23시다. 날짜별 추이가 아니라 전체 수집 기간의 활동 패턴이며, 현재 키만으로 주간·월간 통계를 재구성할 수 없다.

PostgreSQL과의 구분
프로젝트의 PostgreSQL + asyncpg는 별도 도도새 게임 전적 저장 계층이다. 이 자료의 채팅·통화·Discord 게임 활동 통계는 DynamoDB를 사용한다.
04 / SYSTEM DESIGN

이벤트가 들어오면 무엇을 쓰는가

원본 메시지를 모두 보관하는 대신 필요한 집계값과 진행 중 상태를 저장한다.

01 / MESSAGE

카운터 증가

on_message → 봇·DM 제외 → chat_stat와 chat_hourly를 ADD로 증가. 두 테이블 갱신 전체가 하나의 트랜잭션은 아니다.

02 / VOICE

세션 종료 시 합산

입장 → 열린 세션 저장. 퇴장 → 경과 시간 계산 → 누적·시간대 갱신 → 열린 세션 삭제. 채널 이동은 통화 횟수 증가에서 제외.

03 / PRESENCE

게임 상태 변경 추적

음성 채널 안에서 playing 상태를 추적한다. 게임 변경·종료·퇴장 시 경과 시간을 게임별 집계에 더한다.

통화는 시간 경계를 나눠 집계한다

예시: KST 21:50 입장 → 23:10 퇴장 / 총 80분

21시 구간10분
22시 구간60분
23시 구간10분

완료 세션의 누적 시간은 최대 24시간으로 제한한다. 음소거 변경처럼 채널이 같은 이벤트는 통화 구간을 나누지 않는다.

05 / SYSTEM DESIGN

함께 통화한 시간은 쌍으로 쌓는다

참여자 구성이 바뀌기 직전, 기존 구성의 모든 두 명 조합에 경과 시간을 반영한다.

A · B · C같은 음성 채널에서 10분
→
A–B / A–C / B–C각 조합에 10분씩 누적
→
통화 상대 순위개인 상위 상대 / 서버 최장 조합
같은 채널에 머문 시간이다. 실제 발화나 친밀도를 측정하지 않는다. 여러 상대의 시간이 동시에 쌓이므로 상대별 시간의 합은 개인 통화 시간보다 클 수 있다.

저장된 누적값에 현재 활동을 더한다

종료할 때만 저장하는 세션의 특성을 조회 시점의 계산으로 보완한다.

표시할 활동량 = DB 누적값 + 진행 중 세션 경과 시간

서버·집계 종류별 결과를 프로세스 메모리에 30초간 보관한다. Redis는 사용하지 않는다.

사용자 정보 캐시

API로 조회한 표시 이름과 아바타는 서버·사용자별로 10분간 보관한다.

SNAPSHOT

요청 시점의 이미지

통화·게임·통화 상대의 현재 경과 시간을 합산한다. 전송한 PNG 자체가 계속 갱신되는 방식은 아니다.

캐시와 세션 종료의 시점 차이로 일시적인 표시 지연이 생길 수 있다. 화면의 즉시 일관성이나 정확히 한 번의 이벤트 처리를 보장하는 구조는 아니다.

07 / SYSTEM DESIGN

과거 데이터와 재시작을 처리하는 방법

메시지는 백필로 채우고, 진행 중 세션은 현재 Discord 상태와 대조한다.

BACKFILL

과거 메시지 채우기

시작 Snowflake 상한 설정
↓
텍스트 채널 이력 역방향 탐색
↓
200개 읽을 때마다 사용자·시간대 집계
↓
집계 반영 후 커서와 완료 상태 저장

조회 경로에서 작업 완료를 기다린다. 권한 없는 채널은 제외되며, 재분석은 채팅 집계와 커서를 지우고 다시 수행한다.

RECONCILIATION

열린 세션 이어받기

봇 준비 완료
↓
DB 열린 세션 ↔ 현재 채널 상태 비교
↓
현재도 통화·같은 게임이면 이어받기
↓
이미 종료된 세션은 삭제

봇이 꺼진 동안의 정확한 퇴장 시각은 복원할 수 없다. 통화 상대의 구성 추적은 재시작 시점부터 다시 시작한다.

백필 집계와 커서 저장은 원자적이지 않다. 장애 후 재처리나 실시간 수집과의 경계에서 중복 집계 가능성이 있어, 향후 멱등성·경계 관리가 필요하다.
