# 음악 재생 장애 대응

작성일: 2026-08-20

## 배경

Discord 음악 기능에서 곡이 재생 중 갑자기 넘어가는 현상이 반복적으로 관측됐다.
초기 분석 결과, 주된 원인은 봇 큐 로직 자체보다 Lavalink의 YouTube 소스 계층 실패였다.

실제 로그에서 확인한 대표 패턴:

- `dev.lavalink.youtube.AllClientsFailedException`
- `This video requires login`
- `Video player configuration error`
- `java.io.EOFException`
- `Something went wrong when decoding the track`

즉, 일부 곡은 YouTube 플러그인이 스트림을 정상적으로 열지 못해 비정상 종료되고,
기존 봇 로직은 이를 곧바로 다음 곡 진행으로 처리해서 사용자 입장에서는 "강제 스킵"처럼 보였다.


## 초기 문제점

기존 [bot/cogs/music/__init__.py](../bot/cogs/music/__init__.py) 의 `on_wavelink_track_end`는
정상 종료가 아닌 경우에도 대부분 다음 곡으로 진행했다.

이 구조의 문제:

- 일시적 스트림 끊김도 즉시 스킵으로 보임
- 재생 위치를 기억하지 않아 복구 시 항상 처음부터 재생
- 어떤 에러가 "재시도 가치가 있는지"와 "거의 안 살아나는지"를 구분하지 않음


## 목표

우선순위는 다음과 같이 정리했다.

1. 사용자 입장에서 곡이 최대한 안 끊기게 할 것
2. 비정상 종료 시 같은 곡을 가능한 한 복구할 것
3. 무조건 다음 곡으로 넘기는 자동 스킵을 줄일 것
4. 단, 로그인 요구/플레이어 설정 오류처럼 복구 가치가 낮은 에러는 무한 루프에 넣지 않을 것


## 현재 적용한 정책

### 1. 재생 위치 저장

`on_wavelink_player_update` 이벤트에서 현재 재생 위치(ms)를 계속 저장한다.

용도:

- 비정상 종료 후 이어 재생
- 복구 직후 얼마나 안정적으로 버텼는지 판단


### 2. 실패 체인 기준 복구

재시도 카운트는 곡 메타데이터 기준이 아니라 현재 런타임 `Track` 인스턴스 기준이다.

의미:

- 같은 곡이라도 나중에 새로 추가되면 새 재생으로 취급
- 과거 실패 이력이 이후 재생까지 오염되지 않음


### 3. 이어 재생 복구

비정상 종료 시 마지막 저장 위치가 충분히 쌓여 있으면 그 위치부터 다시 시도한다.

현재 기준:

- `MIN_RESUME_MS = 5000`
- 5초 이상 재생된 뒤 죽은 경우에만 이어 재생 시도
- 그보다 짧으면 0초부터 다시 시도


### 4. 실패 체인 초기화

복구 후 일정 시간 이상 재생되면 "같은 장애가 계속 이어지는 상태"로 보지 않고
새 실패 체인으로 간주한다.

현재 기준:

- `RETRY_CHAIN_RESET_MS = 1000`

즉 복구 후 1초만 지나도 새 복구 기회를 다시 부여한다.


### 5. 자동 스킵 최소화

정상 종료(`finished`)나 사용자의 `!음악 스킵`이 아니면
기본적으로 다음 곡으로 자동 진행하지 않는다.

현재 동작:

- `track_end` 비정상 종료 -> 같은 곡 재복구 예약
- `vc.play(...)` 시작 단계 실패 -> 같은 곡 재복구 예약

재복구 딜레이:

- `RETRY_RESTART_DELAY_SEC = 1.0`


## 에러 유형별 분리 정책

### 계속 복구 대상

다음 계열은 일시적 스트림/디코딩 문제일 수 있어 자동 복구를 계속 허용한다.

- `EOFException`
- `Something went wrong when decoding the track`
- 기타 일시적 재생 실패


### 치명적 재생 불가로 분류

다음 계열은 현재 환경에서 재시도 가치가 낮다고 판단한다.

- `requires login`
- `Video player configuration error`
- `playability status` 관련 오류

이 경우:

- 곡을 자동 스킵하지는 않음
- 하지만 무한 자동 복구 루프에는 넣지 않음
- 큐 맨 앞에 둔 채 자동 복구를 멈춤

즉 "자동 스킵 없음"과 "쓸모없는 무한 재시도 방지"를 동시에 노린 상태다.

## 운영 중 확인해야 할 로그

Lavalink:

```bash
docker compose logs -f lavalink
```

봇 음악 로그:

```bash
docker compose logs -f bot | rg "\[Music\]"
```

중요 로그 문자열:

- `비정상 종료`
- `자동 복구 예약`
- `이어 재생 복구 성공`
- `재생 안정화로 실패 체인 초기화`
- `TrackException`
- `치명적 재생 불가로 분류`
- `치명적 오류로 자동 복구 중단`


## 현재 한계

이 문서 시점 기준으로 근본 원인은 여전히 YouTube 소스 계층에 있다.

특히 Lavalink 로그에서 반복 확인된 문제:

- `AllClientsFailedException`
- `WEB/ANDROID_VR requires login`
- `WEB_EMBEDDED_PLAYER configuration error`
- `TVHTML5` 스트림 파싱/디코딩 실패

즉, 봇 쪽 복구 로직은 "증상 완화"에는 효과가 있지만
YouTube 플러그인 자체의 접근 제한이나 스트림 디코딩 실패를 완전히 해결하지는 못한다.


## 후속 후보

비용을 크게 늘리지 않는 범위의 후속 대응 후보:

1. `lavalink/application.yml`의 client 구성 재조정
2. `ANDROID_VR` 제거 검토
3. 필요 시 `WEB` 계열 옵션 보강
4. 계속 실패하는 곡의 에러 유형 통계 수집

운영 비용이 커지는 후보:

1. 별도 remote cipher 자체 호스팅
2. YouTube 보조 컴포넌트 추가 운영

현재 판단으로는 소규모 서버에서는 먼저 봇 복구 정책 + Lavalink 설정 튜닝으로 버티는 쪽이 맞다.
